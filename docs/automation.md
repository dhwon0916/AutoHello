# Automation internals

[Usage and build instructions](../README.md).

Control runtime IDs are compared directly as integer sequences, avoiding string formatting during each eligible-field inspection. Missing or empty IDs fail the final identity comparison. Dialog history is independent of the control ID, so recreating a control never permits a second attempt in an already attempted dialog.

Each focused-element lookup batches the eight eligibility and identity properties in an element-only UI Automation cache request. The snapshot is fetched again on every inspection, including final validation; no element snapshot is reused between inspections. A separate label-name read is needed only when the field's own name does not identify a PIN. Protected values and text are never requested. This reduces separate property requests; live Windows Hello latency has not been benchmarked.

During paced entry, a focus notification schedules cancellation immediately instead of waiting for the next character or Enter deadline. The selected temporary override is checked before focus cancellation and provider inspection, and again after final validation. A held override cancels only the recorded prompt, retaining the configured PIN and keeping automation enabled for other prompts. With an override configured, paced waits wake at most every 50 ms to sample the key without inspecting accessibility metadata before the segment deadline. A focus-invalidated attempt is canceled without another provider call, and focus/readiness/modifier interruptions leave automatic entry enabled even when the skip key has already been released. Its attempt record remains blocked in every case. Actual input failures still pause automation. Inspection exceptions cancel pending input and retry detection after a bounded cooldown without changing the enabled setting. Regression checks cover both delays at their maximum supported value, skips coinciding with focus changes or loss of field readiness, the real worker loop polling during long waits, and the checkbox/tray staying enabled for subsequent prompts.

## Detection and lifecycle

Rapid readiness polling is limited to a foreground process verified as the Windows credential broker. An inspection of an unrelated app ends the readiness burst and returns to the configured idle interval; a new focus event still schedules prompt detection immediately subject to event spacing. A detected broker whose PIN field is still being created retains the short readiness checks. Regression tests verify both paths and preserve the existing 350 ms synthetic delayed-field result. Repeated focus notifications update cancellation and readiness state but signal the worker only when there is no pending inspection. Process-path queries reuse a thread-local buffer; every lookup still opens the process and reads its creation time and path afresh.

One background MTA thread owns all UI Automation calls and subscribes to focus-change events. Foreground changes use `SetWinEventHook` with `WINEVENT_OUTOFCONTEXT` on the existing WinForms message-loop thread, including changes to AutoHello's own windows. The callback delegate is rooted until unhooked. Neither callback reads accessibility metadata or stores a PIN: it only invalidates the focus epoch and signals one coalesced request. The foreground hook is removed on the registering UI thread; UIA subscription and removal both run on the MTA worker.

With default delays, enabling schedules immediate inspection. Explicit paused, watching, stabilizing, and attempted states select an infinite paused wait, a two-second missed-event fallback, or 200 ms stabilization checks. Event bursts coalesce into at most one pending request with a 50 ms minimum spacing. There is only one inspection thread and never a queue of work items. While paused, notifications do not schedule inspections. If event registration fails, a diagnostic reports fallback operation. Process handles are still opened afresh: path and creation time are queried together, so a cached PID/path is never trusted. The usual path buffer is 512 characters, growing to 32,768 only when required.

With default delays, after a foreground/focus notification, watching checks run every 100 ms for up to 1.5 seconds after the most recent event. This catches a PIN field that becomes ready just after the notification, without waiting for the two-second fallback. If no eligible field appears, checking returns to the idle interval. Stabilization schedules its last check at the 200 ms deadline instead of rounding up to the next 200 ms tick; final eligibility and cancellation checks still run. A deterministic fake-provider test with an event at 10 ms and a field available after the first check produces input at 350 ms, versus 850 ms with the prior 700 ms stability delay. This is a scheduling measurement, not a measured Windows sign-in time: provider delays, missed events, focus changes, and Windows authentication processing can still add time.

The stable-field delay uses monotonic `Stopwatch` time and uses your configured duration (200 ms by default). An observation gap exceeding the configured stabilization interval plus one second restarts it. The shorter delay gives the prompt less time to settle and increases accidental-entry risk; it does not mean instant sign-in. A complete final eligibility inspection must match the candidate, followed by another foreground/process identity check. Inspections or final validation taking more than 300 ms are discarded. Focus-event epochs and configuration cancellation tokens invalidate results after focus changes, pause/resume, PIN edits, Enter preference changes, or shutdown. Pause/edit cancellation is published before acquiring the short send lock and rechecked immediately before sending. These are stale-result checks, not COM timeouts. A hung provider cannot be safely aborted: the sole worker may remain stuck, but cannot send after cancellation and does not keep the process alive on exit. No replacement workers are spawned. UIA unsubscription must wait for that call to return on its owning thread; the foreground hook can still be removed promptly on the UI thread. Process exit is the final cleanup boundary if a provider never returns.

Attempts are marked **before** calling `SendInput`, including zero/partial results or exceptions. Records include HWND, PID, and process creation time, survive pause/resume, and are retained for this app session. Reused HWNDs in a different process lifetime are distinct. Same-process HWND reuse cannot be reliably distinguished from an existing dialog, so it remains blocked, even after an observed disappearance. This deliberately may skip a newly reopened prompt. At 4,096 records automation pauses rather than evicting records and risking a retry. Close credential prompts before restarting AutoHello; attempt history is not persisted across app restarts.

Partial/failed input and exceptions during sending pause automation and update the tray and checkbox together. Inspection exceptions retain the enabled setting and retry detection after a 1/2/4/8-second capped cooldown; events and manual re-enables cannot bypass it. A paced attempt interrupted by an inspection exception remains recorded and cannot resume or retry. There are no automatic input retries. The saved enabled preference changes only when Save is clicked. Ordinary detection transitions are deduplicated, stale queued notices are rejected, and routine notices do not overwrite persistent errors or attempt results. Settings actions or explicitly toggling automation can replace these messages. Identical successfully saved preference values are not written again. Reads enforce size limits on an open file before allocation and reject malformed preferences, invalid UTF-8, invalid DPAPI ciphertext, and oversized decoded PINs. Task Scheduler COM objects are released in reverse ownership order, including intermediate property objects and failure paths. A mismatched startup executable or unexpected task action is reported explicitly and never silently repaired. Form disposal stops the worker and disposes tray resources even when the form was never shown.

Notifications can be delayed or missed, and fallback polling cannot detect every focus excursion. Checks and `SendInput` are not an atomic, target-bound operation: focus can change immediately after validation or while Windows processes the input. Pause/exit cannot retract an input batch already submitted. Held Shift, Ctrl, Alt, or either Windows key postpones entry, resets stability, and returns to the low-frequency fallback until release is observed. AutoHello never releases the user's keys. `GetAsyncKeyState` samples can race or be unavailable; they are another conservative check, not a guarantee. `SendInput` reports inserted events, **not authentication success**; its failure information does not reliably identify UIPI blocking. No secure-desktop bypass or security-policy changes are attempted.

No representative live Hello accessibility tree was inspected during this change. AutomationId values and surrounding control structure remain unverified. Recognition still requires the exact broker path, matching process identity, focused/enabled password Edit control, and an accessible PIN label. No undocumented selectors or additional accepted hosts were added. Recreating the PIN control changes its runtime ID and restarts stabilization before an attempt, but never permits another attempt inside an already-attempted dialog.
